See who your change breaks, before you push.

Our services call each other all day. When you change one of them, another can quietly break. The impact reviewer reads your change, finds every service that depends on it, and tells you which ones are at risk.

Without it

You change an API in your service. Your own tests pass and you ship. A day later another team's service starts failing, because it was calling that API the old way.

With it

Before you merge, it shows you that the other service calls this API, where in its code, and whether your change will break it. You fix it now, or ship both changes together.

  • API callsOne service calling another's HTTP endpoint.
  • MessagesOne service publishing to Kafka, SQS, SNS, RabbitMQ, Redis or Celery, and another listening.
  • Shared codeFunctions used in many places within your own service, especially ones that write to the database.
  • Broken codeTypos, missing imports and syntax errors your change introduces.

How it works

Think of your services as stations on a transit map, and the calls between them as lines. The tool draws that map ahead of time, then for every change it follows the lines out from the station you touched. Step through it below.

How to use it

The simplest way is a comment on your pull request. There is nothing to install and nothing to run on your machine.

  1. 1

    Open a pull request

    As you normally would, on any service that has the review switched on.

  2. 2

    Comment /impact-reviewer

    Anyone with write access to the repository can do this. A reaction appears on your comment to show it has started.

  3. 3

    Read the reply

    About a minute later, a comment lists every service your change could affect. Comment again after you push more changes, and the same comment is updated.

Switching it on for your team

An organization admin does this once. After that, nobody else has to set anything up.

  1. 1

    Add the secrets

    A read-only access token that can see every service, shared as an organization secret. Optionally an Anthropic API key, which adds a written risk assessment to the reply.

  2. 2

    Allow sharing

    Let the repositories in the organization use the review workflow that lives in the tool's repository.

  3. 3

    Build the map, add the trigger

    Run the map build once. It then refreshes every night. Add a short workflow file to each service so its pull requests can use the comment.

Prefer to run it on your own machine?

This route needs the tool locally. Clone the repository, check out the branch that has it, and install it into a virtual environment with pip. You also need Python 3.8 or newer, git, and your services cloned. Then ask Kiro chat to set up the impact reviewer: it asks which services to cover, builds the map, and shows any matches it isn't sure about.

Best for everyday work.

  1. Once, set which service to review and which branch to compare against, such as master.
  2. Check out your branch.
  3. Type @review in Kiro chat, or click Cross-Repo Impact Review in the Agent Hooks panel.
  4. The report appears in chat.
# in Kiro chat @review Reviewing: feature/lead-source vs master

Best for a one-off review of any branch.

  1. Name the service, the base branch and your branch.
  2. It compares your branch with the point where it split from the base, then puts your checkout back where it was.
  3. Leave out the branches to review just your last commit.
# your branch vs master bash review.sh -r lead-management-service \ -b master -f feature/lead-source # just the last commit bash review.sh -r lead-management-service

Best as a safety net you don't have to remember.

  1. Install the git hook into your service once.
  2. Push as usual. The check runs on the commits you're pushing.
  3. If it finds a high risk to another service, the push stops and tells you why.
  4. To push anyway, add --no-verify.
# once python -m impact_reviewer install-hook \ --repo-path ~/repos/lead-management-service # then, as always git push

Best when one change needs a PR in each of several services.

  1. List each service with its base branch and feature branch.
  2. Type @review-patch in Kiro chat.
  3. It reviews all the branches together. A change in one service plus its matching fix in another counts as coordinated, not as a break.
  4. What it flags is a service whose PR didn't adapt to the change.
# or from the terminal python -m impact_reviewer review-patch \ --pr hrms-adhoc:master:feature/x \ --pr lead-management-service:master:feature/x

What happens when you review

Each review runs the same checks in order, whether it is triggered from a pull request comment or from your own machine. Cheap, exact checks come first, and AI comes last. If your code has an obvious mistake, the review stops early and no AI is used. Pick a case and run it.

Your change:
  1. Pick what to reviewThe pull request against the branch it targets. On your machine, your branch or your last commit. It always says what it's comparing.
    git
  2. Find the changed functionsMaps each changed line to the function or method it sits in.
    unidiff, Python AST
  3. Check the code is validLooks for syntax errors, undefined names and missing imports. Only problems your change introduced count.
    pyflakes
  4. Follow the mapFinds services that call a changed API or listen to a changed topic, plus busy callers inside your own service.
    dependency map
  5. Collect the relevant codePulls out only the functions involved: your code before and after, and the code that calls it.
    Python AST
  6. AI reviews the riskA separate AI reviewer with a clean slate. It can only read this review's output, and it reads at most five code snippets. On a pull request, this step runs only when an API key has been added.
    Claude
  7. You get the reportA short report on the pull request, or in chat: what's high risk, what to do, and what's safe.

Press "Run the review" to see the report build up.

HIGH

The AI can name what will go wrong and for whom. For example, a caller that doesn't send the new field will get errors.

MEDIUM

Whether it breaks depends on something the AI couldn't check from the code.

LOW

The change is safe: it only adds something new, only affects internals, or the caller already handles it.

What it's built with

It's plain Python with no database and no servers of its own. Pull request reviews run in GitHub Actions, and local reviews run on your machine.

Python ASTReads the structure of your code without running it: functions, API routes (Flask, Django, Sanic, FastAPI), HTTP calls (requests, httpx, aiohttp) and message publishers and listeners.
pyflakesCatches typos, undefined names and missing imports before any AI runs.
unidiff and gitWork out exactly which lines changed and compare your branch with its base.
Dependency mapBuilt from all your services every night and stored, so each review takes about a second.
GitHub ActionsRuns the review when someone comments on a pull request, rebuilds the map every night, and posts the findings back on the pull request.
Claude APIWrites the risk assessment in the pull request comment, for teams that add an API key.
Kiro agents and hooksRun the review from chat, the IDE or a git push, and hand the judgement to an AI that starts fresh and can only read the review's output.
